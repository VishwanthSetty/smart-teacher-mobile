# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Smart Teacher — a Flutter (Material 3) mobile client for the **TEACHER** and **STUDENT** roles of an existing backend (`apps/api`, not in this repo). Full spec, screen inventory, entitlement model, and API reference: [docs/PRD.md](docs/PRD.md) — read it before adding any feature. Dart SDK `^3.11.5`. State/DI via Riverpod, navigation via go_router, HTTP via Dio, tokens via `flutter_secure_storage`, data models via freezed + json_serializable, typography via google_fonts.

Key architectural fact from the PRD: there is no BFF tier. The app itself holds the access/refresh token pair and calls `apps/api` directly with `Authorization: Bearer <token>` — see §1.2 and §6.1–6.2 of the PRD.

**Current state: the PRD's screens (auth §5.1, profile §5.2, library §5.4.1–2, My Classes §5.5.1, roster §5.5.2–3, shell §5.7) plus the real video player and PDF reader, plus phases 1–4 of the learning-activity plan** (`docs/2026-09-11-learning-activity-mobile-plan.md` in the `smart-teacher` repo): the Drift-backed outbox and activity cache, the `PlaybackTracker` and its beats, resume, "Mark as read", the History tabs (§5.2), the progress summary (§5.3), the student Home and teacher Dashboard (§5.1, §5.7), Saved/Collections (§5.4), library search and its filter sheet (§5.5), the student's My Tasks (§5.6), and the teacher's assign flow, task list and task detail (§5.8–5.9). **Phase 5 is built too** — the task progress tabs, the individual-student report, `Remind pending`, class progress, the notification inbox, notification preferences, and the push-registration plumbing (§5.9–5.10). **The one deliberate gap is the push provider itself**: no FCM SDK is wired in, because that needs a Firebase project and the native config files that come with it, and mobile plan §8.4 lists the provider as a decision still to be confirmed. `PushTokenSource` is the port it plugs into and `NoopPushTokenSource` is the default — so the app registers no device and the in-app inbox carries everything, which is the same path a denied push permission takes. The flat `/videos` and `/documents` lists (PRD §5.4.3) do not exist. See "What exists today" below before assuming any screen exists.

## Commands

```bash
flutter pub get
flutter run                       # add -d <device> to pick a target
flutter analyze                   # static analysis; must be clean (strict lints, see below)
flutter test
flutter test test/widget_test.dart                          # single file
flutter test --plain-name 'App boots to the splash screen'  # single test by name
flutter build apk --release
```

Codegen — re-run after touching any `freezed`/`json_serializable` model **or the Drift schema in [app_database.dart](lib/src/core/db/app_database.dart)** (`MeEntity`, `AuthTokens`, `CurriculumEntity`, `ContentTreeEntity`/`ContentNodeEntity`/`ContentItemEntity`, `SectionEntity`, `StudentEntity`, `ResourceActivityEntity`, `ProgressSummaryEntity`, `BookmarkEntity`, `CollectionEntity`, `SearchResultEntity`, `TaskEntity`/`TaskAssignmentEntity`/`StudentTaskEntity`, `TaskProgressRowEntity`/`ClassProgressRowEntity`/`TaskReminderResult`, `NotificationEntity`/`NotificationPreferenceEntity`/`DeviceRegistrationEntity`; `*.freezed.dart`/`*.g.dart` are generated, don't hand-edit them). The Drift schema is at **version 2** — adding a column means bumping `schemaVersion` and extending the `MigrationStrategy`, not dropping the database; the outbox holds the user's own unsent writes. `PaginatedResult`, `CursorPagedState`, `LocalActivity`, `OutboxEntry`, `SearchQuery`, `TeacherTaskQuery` and the `home` entities are outside this — generics and plain `core/` types rule out codegen, so their equality and parsing are hand-written:
```bash
dart run build_runner build --delete-conflicting-outputs
```

## Lint contract

`analysis_options.yaml` enables `strict-casts` and `strict-raw-types` plus rules that are *errors in review even when the analyzer only warns*. New code must satisfy them or `flutter analyze` will complain:
single quotes, `const` constructors/declarations wherever possible, `final` locals, explicit return types on every declaration, trailing commas on multi-line arg lists, `unawaited_futures`, `sort_child_properties_last`.

## Architecture

Feature-first under `lib/src/`, with a shared `core/` layer. Entry point [main.dart](lib/main.dart) only wraps [SmartTeacherApp](lib/src/app.dart) in a `ProviderScope`.

Each feature under `lib/src/features/<name>/` uses up to three layers:
- `domain/` — plain immutable models (prefer freezed + json_serializable for anything that round-trips through the API — see PRD §8 for the entity shapes to model: `MeEntity`, `CurriculumEntity`, `TeacherAssignmentEntity`, `StudentEntity`, etc.)
- `data/` — an abstract repository + concrete impl (backed by `dioProvider`) + the Riverpod providers exposing it
- `presentation/` — screens and feature-local `widgets/`

The key invariant carried forward from earlier iterations of this app and still expected of new features: **presentation depends on the repository interface, never the implementation.** Define an abstract repository, expose it through a provider, and override that provider in tests (`ProviderScope.overrides`) rather than mocking at the widget level.

Screens should consume data through `FutureProvider`s (or `AsyncNotifier`) and render `AsyncValue` loading/error states, rather than managing futures in `State`.

### What exists today

- [core/errors/app_error.dart](lib/src/core/errors/app_error.dart) — the sealed `AppError` union (`UnauthorizedError`, `ForbiddenError`, `NotFoundError`, `RateLimitedError`, `ValidationError`, `NetworkError`, `UnknownError`) and `AppError.fromDioException`, the **only** place HTTP status codes are branched on (PRD §6.3). Repositories wrap calls in `guardApiCall(() => ...)` so a `DioException` never escapes the data layer; presentation switches over the variants (exhaustive — no `default`) and never touches `statusCode` or `response.data`. `ForbiddenError.isSchoolSuspended` carries the §5.2 suspended-school signal.
- [core/storage/token_storage.dart](lib/src/core/storage/token_storage.dart) — the `TokenStorage` interface (`saveTokens`/`getAccessToken`/`getRefreshToken`/`clearTokens`/`hasValidSession`) and its `SecureTokenStorage` impl wrapping `flutter_secure_storage`, exposed via `tokenStorageProvider` (typed as the interface — override it in tests). `hasValidSession()` checks refresh-token presence only; token expiry is the server's call, surfaced as a 401. Tokens must never go through `SharedPreferences`, logging, or crash breadcrumbs (PRD §6.1).
- [core/network/dio_client.dart](lib/src/core/network/dio_client.dart) — `dioProvider` is the one `Dio` instance for the whole app (base URL from `--dart-define=API_URL=...`, default `http://localhost:4000`). It carries [AuthInterceptor](lib/src/core/network/auth_interceptor.dart), the one and only home of the token lifecycle (PRD §6.2): attaches the bearer token, refreshes once on 401 (concurrent 401s share a single in-flight refresh) and retries, and on unrecoverable refresh failure clears storage and emits `AuthEvent.loggedOut` via `authEventNotifierProvider`. Never add per-screen retry logic. The `unauthenticatedPaths` set (login, forgot/reset password, refresh) is exempt from both halves: they carry no bearer token, and their 401s are *answers* — refreshing on a mistyped password would hide the real result and force a logout.
- [core/session/session_controller.dart](lib/src/core/session/session_controller.dart) — `SessionController`, the single session gate (PRD §6.6), a `Notifier<SessionStatus>` over `unknown`/`authenticated`/`unauthenticated`. It restores from `TokenStorage.hasValidSession()` at startup, exposes `onSignedIn()`/`signOut()` for the auth feature, and subscribes to `AuthEvent.loggedOut` so a forced logout raised anywhere becomes a redirect. Role is **not** here — it comes from `GET /users/me` and belongs to the profile feature (§5.7).
- [core/router/app_router.dart](lib/src/core/router/app_router.dart) — `routerProvider` builds the `GoRouter`. Its top-level `redirect` is the only place navigation reacts to auth state: `unknown` parks on `/splash` (preserving the intended destination in `?from=`, so a deep link arriving mid-startup isn't swallowed), `unauthenticated` allows only `AppRoutes.public` and sends everything else to `/login`, `authenticated` bounces public routes to `/home` — except `/reset-password`, which is exempt because it arrives by emailed deep link and revokes all sessions on success (§5.1.4). A session change re-runs the redirect through `refreshListenable`; the provider `listen`s rather than `watch`es so the nav stack survives. Never hardcode path strings; add to `AppRoutes` — parameterised routes (`/curricula/:id/tree`, `/videos/:id`, `/documents/:id`) get a `*Path` builder there rather than being interpolated at the call site. Those three are pushed over the shell and each takes its label through `extra`, which is a nicety and not a dependency: `extra` doesn't survive a deep link or a process restart, so every one of them falls back to a title it can derive itself.
- [features/auth](lib/src/features/auth/) — login (§5.1.1) and forgot/reset password (§5.1.4). [AuthRepository](lib/src/features/auth/data/auth_repository.dart) wraps all three endpoints. Each screen has a `Notifier` controller + a sealed failure type in `presentation/`, and they share [auth_validators.dart](lib/src/features/auth/presentation/auth_validators.dart) (one wording per rule across screens), [retry_countdown.dart](lib/src/features/auth/presentation/retry_countdown.dart) (the `429` window, ticked down so the button re-enables itself; never invents a duration when there's no `Retry-After`) and [widgets/auth_banner.dart](lib/src/features/auth/presentation/widgets/auth_banner.dart) (in-page, tone-aware — error vs. waiting vs. success; not a snackbar, since every one of these needs the user to *do* something). [LoginController](lib/src/features/auth/presentation/login_controller.dart) owns the whole sequence (login → persist tokens → `GET /users/me` → `currentUserProvider` → `SessionController.onSignedIn()`), rolls the tokens back if any step after persisting fails, and maps `AppError` onto the closed set of [LoginFailure](lib/src/features/auth/presentation/login_state.dart) states the PRD asks for (401 → one message for all three fields, 403 → disabled vs. suspended, 429 → a waiting state that counts the `Retry-After` window down). **It never calls `context.go`** — opening the session is what navigates, via the router redirect.
- [features/profile](lib/src/features/profile/) — the data login needs plus the Profile/"Me" screen (§5.2). Data: [MeEntity](lib/src/features/profile/domain/me_entity.dart) (freezed, PRD §8.2; `UserRole`/`SchoolStatus` both carry an `unknown` fallback so an unexpected value can't crash deserialisation), [ProfileRepository](lib/src/features/profile/data/profile_repository.dart) for `GET /users/me`, and [currentUserProvider](lib/src/features/profile/data/current_user_controller.dart) — the app-wide signed-in actor, which clears itself when the session ends. **Read the role from here**, never assume one (§5.7). Screen: [ProfileView](lib/src/features/profile/presentation/profile_view.dart) (name, email, [RoleBadge](lib/src/features/profile/presentation/widgets/role_badge.dart), school name, sign-out — plus the suspended-school takeover) holds all of it as a bare body with no `Scaffold`, because two things render it with different chrome: [ProfileScreen](lib/src/features/profile/presentation/profile_screen.dart) wraps it for the `/profile` route, and the student shell drops it straight into its Profile tab under the shell's own app bar. It runs over [ProfileController](lib/src/features/profile/presentation/profile_controller.dart), an `AsyncNotifier` that **serves the profile login already cached and only refetches on pull-to-refresh** — a fetch in `build` happens solely on a restored session, where nothing populated the cache. Whatever it fetches is written back to `currentUserProvider` so the screen and the shell can't disagree. Riverpod's automatic retry is switched off (`retry: … => null`): the error state offers an explicit "Try again", and a background retry loop against a suspended school just 403s forever.
- **The curriculum tree, §5.4.2** — the drill-down behind a library card, and the second half of the library feature. [ContentNodeEntity](lib/src/features/library/domain/content_node_entity.dart) is one recursive entity for both chapters and sub-topics (they are the same shape at every depth), carrying its own `videos[]`/`documents[]` of `ContentItemEntity` plus `videoCountDeep`/`documentCountDeep`. **Those two counts are the contract**: they already describe the whole subtree, so [ContentNodeTile](lib/src/features/library/presentation/widgets/content_node_tile.dart) greys out and refuses to expand an empty branch from a field read — never by walking `children`. Recomputing them client-side would be both wasted work and a second, disagreeing source of truth. [ContentTreeRepository](lib/src/features/library/data/content_tree_repository.dart) reads `GET /curricula/:id/tree` (tolerating either an envelope object or a bare array of chapters, and either `children` or `nodes` for sub-nodes — the PRD names the payload without pinning its keys); [CurriculumTreeController](lib/src/features/library/presentation/curriculum_tree_controller.dart) is shaped like `LibraryController` but is an **auto-disposing family** keyed by curriculum id, so opening twenty curricula doesn't pin twenty trees for the session. **A `404` here is the entitlement answer** (§4: the endpoint answers `404` both for "no such curriculum" and for "exists, but not yours", so a single-item read can't leak more than the list) — [CurriculumTreeScreen](lib/src/features/library/presentation/curriculum_tree_screen.dart) renders [NotFoundView](lib/src/core/widgets/not_found_view.dart) for it, with no retry and no wording that could read as a refusal. Its `403` handling is the sharper cousin of the library's: entitlement refusals arrive as `404` here, so a suspension-flavoured `403` can only be a suspension and `confirm()`s the latch on the first answer. Tapping a video or document row pushes [ContentItemStubScreen](lib/src/features/library/presentation/content_item_stub_screen.dart) (`/videos/:id`, `/documents/:id`) — the route carries the item id so the real player/reader drops in behind it unchanged; the id is deliberately *not* displayed.
- **Suspended-school detection (§5.2)** spans three files. [SuspensionInterceptor](lib/src/core/network/suspension_interceptor.dart) sits behind `AuthInterceptor` in the shared Dio pipeline and observes every authenticated call — it never resolves or rejects anything, and it does *not* branch on `403`; it asks `AppError.fromDioException` and matches `ForbiddenError(isSchoolSuspended: true)`. It feeds [schoolSuspensionProvider](lib/src/core/session/school_suspension_controller.dart), the single app-wide latch: **two** suspension-flavoured 403s in a row confirm it (one alone can be an ordinary entitlement refusal), an authoritative answer from `/users/me` (`school.status == SUSPENDED`, or a 403 that reads as one) confirms it immediately via `confirm()`, and any successful authenticated call — or the session ending — clears it. A screen watching the latch renders [SchoolSuspendedView](lib/src/core/widgets/school_suspended_view.dart) instead of its own content; it takes an `onSignOut` callback because `core/` must not import a feature. **Do this on every new screen** — the point of §5.2 is one explanatory screen, not the same generic error everywhere.
- [LogoutController](lib/src/features/auth/presentation/logout_controller.dart) — sign-out (§5.1.3), stateless because there is no failure the user can act on. Local-first: it reads the token pair, fires `POST /auth/logout` **unawaited** (passing both tokens explicitly, since storage is about to be empty when the interceptor's `onRequest` runs), then clears storage and flips the session gate. An `AppError` from the revoke, or an unreadable keystore, is swallowed — the user is signed out either way. Like the login controller it never calls `context.go`; the redirect does that. `/auth/logout` is in `unauthenticatedPaths` for the mirror of the login reason: it carries its own header, and a 401 there is the answer, not a session to refresh. The button lives on the profile screen (§5.2), and on `SchoolSuspendedView` — where it is the only action, since a suspension lasts the access token's lifetime and nothing else the user does from the app can change it.
- [ForgotPasswordController](lib/src/features/auth/presentation/forgot_password_controller.dart) — the non-disclosure rule is enforced here, not in the widget: 401/403/404 are folded into the *same* confirmation a 200 produces, so no outcome reveals whether an account exists (§5.1.4). Only failures meaning the request never happened (network, timeout, 5xx) are shown, because "check your inbox" would otherwise be a lie. Its `429` copy is deliberately distinct from login's lockout.
- [ResetPasswordController](lib/src/features/auth/presentation/reset_password_controller.dart) — takes the token from `?token=`; **actual deep-link registration is not wired up** (still an open backend question, PRD §9.2). On success it calls `SessionController.signOut()` before the screen routes to `/login`: the reset revokes every session server-side, so any local tokens are already dead. A null or server-rejected token replaces the form with a "request a new link" state. New passwords get a client-side length floor + confirmation match + an advisory strength meter ([password_strength.dart](lib/src/features/auth/presentation/password_strength.dart)); the API stays the authority and its rejections are shown verbatim.
- [features/shell](lib/src/features/shell/) — the role-based navigation shell (§5.7), which is what `/home` now is. [shellTabsFor](lib/src/features/shell/domain/shell_tab.dart) is **the one and only place in the app allowed to look at `MeEntity.role`** (Teacher: My Classes · Roster · Library; Student: Library · Profile; `UserRole.unknown` degrades to a Profile-only shell so an unrenderable role can't strand a user without sign-out). [AppShell](lib/src/features/shell/presentation/app_shell.dart) is one widget, not two — everything downstream is derived from the returned tab list, including whether the app bar needs a profile action to keep sign-out reachable (it does for a teacher, whose tab set has no Profile tab; it pushes `/profile`). If a new screen wants to branch on the role, that branch belongs in `shellTabsFor` as a different tab set. The shell owns the app bar and the tab bar, so **tab bodies return bare bodies, not `Scaffold`s.** It reads the role off `profileControllerProvider`, so the normal path paints the right tabs on the first frame and the loading/error states are the restored-session case; a confirmed suspension replaces the whole shell, tab bar included.
- [features/library](lib/src/features/library/) — the curriculum list, "My Library" (§5.4.1). [CurriculumEntity](lib/src/features/library/domain/curriculum_entity.dart) (freezed, §8.3; `CurriculumAudience`/`CurriculumStatus` carry an `unknown` fallback, and the three counts default to `0`, so one odd row can't fail the whole list), [CurriculumRepository](lib/src/features/library/data/curriculum_repository.dart) for `GET /curricula`, and [LibraryController](lib/src/features/library/presentation/library_controller.dart) — an `AsyncNotifier` shaped like `ProfileController` (same `refresh()`, same `retry: … => null`) except that it always fetches in `build`, since nothing earlier in the app caches curricula. **The list is server-scoped by role and entitlement (§4) and this feature adds no filtering of its own** — it does not read `MeEntity.role`, and it deliberately does not pass the endpoint's optional `?audience=` parameter, because the only thing it could derive that from is the role. [LibraryScreen](lib/src/features/library/presentation/library_screen.dart) renders three distinct outcomes: rows of [CurriculumCard](lib/src/features/library/presentation/widgets/curriculum_card.dart), a **designed empty state** for `200 []` (§6.4 — an unentitled school and a student with no active enrollment both land there, and its copy names neither role, since which cause applies is a server-side fact the screen can't see), and an error state with a retry. Cards push the tree (§5.4.2), handing the subject name along as `extra` so it can title itself before its own fetch answers; a card whose counts are all zero is still tappable, since the counts are a snapshot and the tree has an empty state of its own. A suspension-flavoured `403` here calls `confirm()` on the latch immediately rather than waiting for the interceptor's two-in-a-row pattern: `/curricula` is already scoped to exactly this actor's entitlements, so there is no narrower entitlement it could have been refused by.
- [features/classes](lib/src/features/classes/) — My Classes, the teacher's assignment list (§5.5.1). **`GET /teacher-assignments` is the one endpoint in the app that is *not* auto-scoped to the caller**: a bare call returns every assignment in the school, with a `200`, which is indistinguishable from success anywhere above the wire (§5.5.1, §9.3). [TeacherAssignmentRepository](lib/src/features/classes/data/teacher_assignment_repository.dart) therefore takes `teacherId` as a **required named argument** rather than reading it from a provider, and refuses to issue the request at all when it is blank — `?teacherId=` is the unscoped call wearing a disguise. The id comes from the cached [currentUserProvider](lib/src/features/profile/data/current_user_controller.dart), which [MyClassesController](lib/src/features/classes/presentation/my_classes_controller.dart) *watches*, so a profile refreshed into a different actor re-reads rather than leaving the previous teacher's classes on screen; with no cached profile it throws instead of calling, since an unscoped success is worse than an error state. [TeacherAssignmentEntity](lib/src/features/classes/domain/teacher_assignment_entity.dart) models `sectionId`/`sectionName`/`gradeLevelId`/`gradeLevelName`/`sectionLabel` as **nullable together** — that is the legacy school-wide grant from bulk CSV import, a valid assignment and not a malformed row — and turns the pair into the one string §5.5.1 specifies: `displayLabel` is `'Mathematics — Grade 5 - A'` or `'Mathematics — all sections'`, so [AssignmentCard](lib/src/features/classes/presentation/widgets/assignment_card.dart) renders both forms as one layout with a caption explaining the school-wide case. Rows are deliberately **not tappable** — §5.5.1 specifies a list, and although the roster (§5.5.2) now exists and filters by exactly these `sectionId`s, wiring a row to pre-filter it would be a navigation the PRD doesn't ask for. Unlike the library, a suspension-flavoured `403` here does **not** `confirm()` the latch: `SuspensionInterceptor` already observes this call, so self-reporting would turn one `403` into the two-in-a-row it treats as corroboration, and this endpoint is role-gated rather than entitlement-scoped, so its `403` has an innocent reading `/curricula`'s does not.
- **The section lookup, §5.5.3** — a data source with no screen of its own, feeding the roster's filter picker. `GET /sections` exists only because `GET /students` takes `sectionId` as an **opaque filter** and returns no joined section list, so the roster's "filter by section" picker has no other way to turn ids into names. [SectionEntity](lib/src/features/roster/domain/section_entity.dart) is the one entity in the app the PRD names without pinning a shape (§8 stops at `StudentEntity`) — it is modelled from the two places the same fields already arrive, `StudentEntity.enrollment` and `TeacherAssignmentEntity`, so only `id` and `name` are required and `displayLabel` follows the same precedence as `TeacherAssignmentEntity.classLabel` (server-composed `label` wins; the grade/name join is the fallback). [SectionRepository](lib/src/features/roster/data/section_repository.dart) takes **no arguments and adds no filtering**: the endpoint is role-gated (§8.6) and answers with the caller's whole school. §5.5.2's suggestion to *default* the filter to a section the teacher actually teaches is a client-side choice made from `/teacher-assignments` ids by whatever consumes this list — not a narrowing baked in here, which would also break a teacher browsing beyond their own classes. Unlike `/teacher-assignments`, the unqualified call is the correct one. [SectionsController](lib/src/features/roster/presentation/sections_controller.dart) is shaped like `LibraryController` but is deliberately **not auto-disposing**: a picker is opened and dismissed repeatedly over one visit, and a school's sections are near-static, so disposal would cost a request per tap. Like My Classes and unlike the library, it does **not** `confirm()` the suspension latch — `SuspensionInterceptor` already observes this call, and a role-gated `403` has an innocent reading.
- **Pagination, §6.5** — `core/pagination/` plus [PaginatedListView](lib/src/core/widgets/paginated_list_view.dart), the **one** reusable paginated list the PRD asks for. `GET /students` is the only **page-numbered** endpoint; `GET /me/activity` is **cursor**-paginated and gets [CursorPagedState](lib/src/core/pagination/cursor_paged_state.dart) instead (see below). Every other list endpoint returns a flat array and gets a plain `ListView` with no paging affordance. [PaginationConstants](lib/src/core/pagination/paginated_result.dart) holds the wire contract (1-based pages, default `limit=20`, hard ceiling `100` — clamped in the repository rather than trusted from a call site). `PaginatedResult<T>` is the PRD's `PaginatedStudentsEntity` generalised over its row type; it is the one **hand-written** model in the app, because freezed/json_serializable don't generate for a generic envelope, and it is deliberately forgiving about envelope keys (`data`/`items`/`results`, counters nested or alongside, even a bare array) since §8.5 pins the *row* and not the wrapper — a wrong guess costs a missing count, not a failed screen. `hasMore` prefers the server's flag, then a page count, then a row count, and only then "a full page probably has another behind it", which at worst costs one request answering `[]`. [PagedListState](lib/src/core/pagination/paged_list_state.dart) is the split that matters: **the first page is the `AsyncValue`, every page after it is `isLoadingMore`/`loadMoreError` inside the data**, so a failed page four can never blank pages one to three. It also de-duplicates by identity on append — a roster is a moving table, and the same row arriving on two pages is a duplicate-key crash, not a cosmetic repeat. The widget auto-loads on scroll but **does not re-arm after a failure**: the footer's tap is what retries, so a list parked at the bottom against a failing server doesn't re-issue once a frame.
- [features/roster](lib/src/features/roster/) — My Students (§5.5.2), the app's only paginated screen and the only consumer of §5.5.3. [StudentEntity](lib/src/features/roster/domain/student_entity.dart) (freezed, §8.5) requires **only `id`**: the name fields are what the row draws, but one row missing a surname must not fail a page of thirty, so `displayName` falls through `name` → the parts → the email → the id. `enrollment` is nullable and `null` is the documented **unplaced student**, rendered as an *Unassigned* tag rather than a blank — as is an enrollment carrying nothing to name, since the teacher's answer is the same either way. [StudentRepository](lib/src/features/roster/data/student_repository.dart) sends `page`/`limit` and **omits every blank filter rather than sending it empty**: `?sectionId=` is a parameter the server may read as "no filter" and `?search=` as a term matching nothing, and neither guess should come from an empty text field. Unlike `/teacher-assignments`, the unqualified call is the correct one — `/students` is role-gated and school-scoped (§8.6). The query lives in its own notifier, [rosterQueryProvider](lib/src/features/roster/presentation/roster_query.dart), which [RosterController](lib/src/features/roster/presentation/roster_controller.dart) *watches*, so **changing a filter restarts from page one by construction** rather than by remembering to reset a counter; a page still in flight when the query changes is dropped by generation check rather than appended to a list that has since been re-queried. `RosterQuery` compares on the *trimmed* term, so a trailing space costs no request, and debouncing lives in [RosterSearchField](lib/src/features/roster/presentation/widgets/roster_search_field.dart) — not in the notifier, whose every state change is meant to reach the network. §5.5.2's suggestion to **default** the filter to a section the teacher teaches is deliberately *not* implemented: silently showing a subset on first open is indistinguishable from the school having that few students, and it would make the first page wait on `/teacher-assignments`. The empty state splits in two (§6.4) — "No students match" with a **Clear filters** action when something is narrowing the list, "No students yet" without one when nothing is. Like My Classes and unlike the library, a suspension-flavoured `403` does **not** `confirm()` the latch. **The screen is read-only and must stay that way**: no edit, deactivate, reset-password or create affordance, and [StudentCard](lib/src/features/roster/presentation/widgets/student_card.dart) is not even tappable, because every student write route is SCHOOL_ADMIN-only and out of mobile scope (§5.5.2, §8.6). [SectionFilterButton](lib/src/features/roster/presentation/widgets/section_filter_button.dart) is a sheet rather than a dropdown because the section list is a network call whose three answers (rows, none, an error) each need a sentence, and it watches `sectionsControllerProvider` only once a section is selected — so the picker's list loads on first open, not on the roster's first paint.
- **The sync engine, `core/sync/` + `core/db/`** — the load-bearing half of the learning-activity work (mobile plan §2), built before any screen that writes so no later feature grows its own retry. [watch_interval.dart](lib/src/core/sync/watch_interval.dart) is the pure union/clamp logic, deliberately the same algorithm the server runs: the client merges only to keep the payload small, and **must never add coverage the raw ranges didn't contain**. [PlaybackTracker](lib/src/core/sync/playback_tracker.dart) captures the ranges **actually played** — timer-free and stream-free, every decision a pure function of the position samples pushed into it, which is what makes "a seek emits no interval" a unit test instead of an integration test. A seek closes the open range and opens a new one at the destination, so **scrubbing to the end contributes nothing**; beats flush every 15s of real playback, on every range close, and on dispose. [OutboxEntry](lib/src/core/sync/outbox_entry.dart) stamps `clientUpdatedAt` **at the moment of the user action, never at send time** — the server resolves `positionSecs` and `lastPage` by last-write-wins on that field, so a send-time stamp would silently reorder the user's own history — and carries the per-kind coalescing rules (video unions intervals and takes the newer position; document progress keeps the newer page; a complete/uncomplete pair is last-one-wins, so a double tap collapses to one request). [OutboxStore](lib/src/core/sync/outbox_store.dart) and [ActivityCacheStore](lib/src/core/sync/activity_cache_store.dart) are **interfaces** over Drift ([app_database.dart](lib/src/core/db/app_database.dart)) with in-memory twins, so no test needs a native sqlite binary — override the interface, never `appDatabaseProvider`. [OutboxWorker](lib/src/core/sync/outbox_worker.dart) owns the rules and **no timer of its own**: a `4xx` that is not `408`/`429` is **discarded, not retried** (a `404` means the resource left this user's scope, and replaying it forever wedges the queue), `429`/`5xx`/network back off exponentially, and a `401` stops the drain rather than discarding — the sign-out path clears the queue wholesale. It reaches the API through [OutboxTransport](lib/src/core/sync/outbox_worker.dart), a narrow port the activity feature implements, because **`core/` must not import a feature**.
- [features/activity](lib/src/features/activity/) — progress, history and the progress summary. [ActivitySyncController](lib/src/features/activity/presentation/activity_sync_controller.dart) is **the only way the app writes progress**: it writes the cache optimistically, enqueues, and kicks off a flush it deliberately does *not* await — a beat is durable the moment it is queued, and blocking playback on the round trip would trade the thing that matters for the thing that doesn't. It **never invents a `percent` or a `status`**: video completion is unique coverage against the server-configured `VIDEO_COMPLETION_PERCENT`, so the client must not hardcode 90% and treats a local percent as provisional until a flush confirms. Nothing in presentation calls [ProgressRepository](lib/src/features/activity/data/progress_repository.dart) directly — that is what the outbox is for. [HistoryScreen](lib/src/features/activity/presentation/history_screen.dart) is the Videos/Documents tabs over [CursorPagedState](lib/src/core/pagination/cursor_paged_state.dart); its controller is a family keyed by resource type that *watches* its status filter, so **changing a chip restarts from the first page by construction**. [ProgressSummaryScreen](lib/src/features/activity/presentation/progress_summary_screen.dart) is one widget for both roles because `GET /me/progress/summary` is already actor-scoped — the caller passes `isTeacherPreparation` rather than the screen reading the role, and the teacher's heading says **"My preparation"** so it is never confused with a class report.
- **Documents: opening is not reading.** [DocumentReadingController](lib/src/features/activity/presentation/document_reading_controller.dart) reports the settled page (debounced 1.5s, not on every swipe) and owns the **Mark as read** toggle, which is the *only* way a document reaches `COMPLETED` — reaching the last page does not, and no UI here may imply it does. Reopening restores `lastPage` **directly, with no chooser**, unlike a video: a page is one swipe to correct. `pageCount` stays null until `Document.pageCount` is populated at ingest, so the reader shows a bare `'page 7'` rather than guessing a denominator. It captures the sync controller in `build` because Riverpod forbids touching `ref` inside `onDispose`, and that dispose flush is what saves a page settling as the reader closes.
- **Video resume.** [ResumePrompt](lib/src/features/activity/presentation/widgets/resume_prompt.dart) offers **"Resume · Start over"** only past a ten-second divergence *and* only when the cached row has been synced — an unsynced row is this device's own optimistic write, so the user put the playhead there themselves and there is nothing to ask about. Below the threshold it seeks silently. [VideoProgressReporter](lib/src/features/activity/presentation/widgets/video_progress_reporter.dart) wraps the *screen*, not the playback widget, for two reasons: the engine is replaced on every token re-mint and progress must survive the swap, and full screen is a second route over the same provider that would otherwise double-report. Token re-mint and progress beats stay independent — a failed re-mint must not drop queued beats, and a failed beat must not interrupt playback.
- [features/home](lib/src/features/home/) — the two single-round-trip aggregates (`/home/student`, `/home/teacher`), each role-gated to exactly one role, so calling the wrong one is a `403` rather than an empty screen. Nothing here picks between them: the choice comes from the tab set. The task and bookmark payloads are deliberately **reduced to counts** in [home_entity.dart](lib/src/features/home/domain/home_entity.dart) until phases 3–4 model them properly — a reduction stated in the type rather than a payload silently dropped. A teacher with no **section-bearing** assignment legitimately sees no classes (`TeacherClassScopeService` fails closed), which is an explanatory notice, not an error, and deliberately does not contradict My Classes — that screen reads the broader `/teacher-assignments`, which includes the school-wide legacy grant that carries no section.
- [features/saved](lib/src/features/saved/) — **Saved and Collections (§5.4)**, and the only place the app writes a bookmark. [SavedController](lib/src/features/saved/presentation/saved_controller.dart) is shaped like `ActivitySyncController`: it mutates its own list optimistically, enqueues, and kicks off a flush it deliberately does not await. **Bookmark toggles go through the outbox**, which is why `OutboxKind` gained `bookmarkAdd`/`bookmarkRemove` and `OutboxEntry` gained `resourceKind`/`bookmarkId`/`collectionId` (Drift schema v2, migrated rather than dropped — a queued beat is the user's own unsent write). The add/remove pair **shares one merge key**, so a double tap on the star collapses to one request; a remove that folds onto a still-queued add inherits that add's *absent* `bookmarkId`, and the transport reads a null id as "nothing to delete" — which is exactly right, since the add never reached the server. `isSaved` answers **`null`, not `false`, while the list is loading**: "not saved" and "we haven't asked yet" are different answers, and [BookmarkButton](lib/src/features/saved/presentation/widgets/bookmark_button.dart) renders nothing until it has one. **Collections are deliberately *not* outboxed** — a duplicate name is a `409` the teacher has to see, and a delete un-files items — so [CollectionsController](lib/src/features/saved/presentation/collections_controller.dart) awaits the server and reports failures in place. Deleting a collection **un-files its bookmarks, never unsaves them** (`SetNull`, not `Cascade`), and the confirm dialog says so. [SavedView](lib/src/features/saved/presentation/saved_screen.dart) is one widget for both roles with `withCollections` passed **in** — the student shell drops the flat variant into its Saved tab, the teacher pushes `/saved` for the Collections/Unfiled pair.
- [features/search](lib/src/features/search/) — library search (§5.5). [SearchQuery](lib/src/features/search/domain/search_query.dart) is hand-written (it never round-trips, it is *turned into* query parameters) and compares on the **trimmed** term, so a trailing space costs no request; debouncing (300ms) lives in the field, not the notifier, whose every change is meant to reach the network. **An empty query runs no request at all** — `/library/search` with no `q` and no filters returns the first twenty rows of the whole library, which is the Library tab's answer, not this screen's. Search is **online-only**: a failure surfaces plainly rather than falling back to a partial cache, which would silently hide results. [SearchFilterSheet](lib/src/features/search/presentation/widgets/search_filter_sheet.dart) builds its subject and grade options from `libraryControllerProvider` — the actor's own curricula, which is by definition the set the search is scoped to — and its audience control is `withAudience`, passed in by the caller rather than read from the role. The entry point is a tappable field at the top of the Library tab, not a live one: the shell owns that screen's app bar.
- [features/tasks](lib/src/features/tasks/) — the student's My Tasks (§5.6) and the teacher's assign flow, list and detail (§5.8–5.9). **Nothing here writes a task status.** A task's status is a projection of the linked resource's progress (backend §6), so there is no "mark done" control on the student's list or detail — for a video it closes itself, and for a document the control is the reader's own *Mark as read*, named identically. Two repositories, not one: `/me/tasks` returns **assignments with the task nested** and `/tasks` returns **tasks with the assignments nested**, and folding them together would mean one method that lied about its return depending on the caller. The three sections (Overdue / Due soon / Completed) come from `groupStudentTasks`, a pure function over one unfiltered read — completed wins over overdue, since a task finished late is done. [TaskRepository.createTask](lib/src/features/tasks/data/task_repository.dart) is the one call that reads a status code outside `AppError`: the `422` naming unreachable recipients becomes `TaskRecipientsUnreachable`, because the ids are the actionable part — the assign sheet flags those students and sends the teacher back to step 2 rather than dropping them. [AssignTaskController](lib/src/features/tasks/presentation/assign_task_controller.dart) makes the `400` shapes unreachable: `selectSection` and `selectStudents` each clear the other, since the server takes exactly one. Recipients come from `assignableSectionsProvider`, which reads `/home/teacher`'s `classes` — resolved through `TeacherClassScopeService`, failing closed — **not** the school-wide `/sections`; a teacher with none is told so and the flow stops, matching the server refusing them outright. [ResourcePickerSheet](lib/src/features/tasks/presentation/widgets/resource_picker_sheet.dart) excludes teacher-audience curricula so the `400` for assigning teacher material is unreachable in practice. The detail screen edits **title, instructions and due date only**; the resource and recipients are read-only with the cancel-and-recreate note, and cancel is soft.
- [core/session/session_scoped_cache.dart](lib/src/core/session/session_scoped_cache.dart) — `invalidateOnSignOut(ref)`. **Call it from the `build()` of any non-auto-disposing controller holding server data** (the saved list, collections, either task list). Mobile plan §0: no resource list survives logout, and a session-held controller would otherwise still be populated when the next user signs in on the same device.
- [core/sync/composite_outbox_transport.dart](lib/src/core/sync/composite_outbox_transport.dart) — routes each `OutboxKind` to the transport that owns its endpoint, so one queue can carry progress *and* bookmark writes while `core/sync` still imports no feature. The routing table is assembled in `outboxTransportProvider` (activity/data), the only place that knows both halves; an unrouted kind throws rather than queueing forever unsent.
- [core/widgets/error_retry_view.dart](lib/src/core/widgets/error_retry_view.dart) — the shared "that call failed, try again" body, with an exhaustive icon switch over `AppError`. New screens use it; the library and My Classes still carry the private copies it was factored out of, and should collapse into it when either is next touched.
- `ComingSoonView` has **no remaining uses** — the player and reader are real. It means "not built yet" and is explicitly *not* an empty state: an unentitled school and an unplaced student are legitimate zero-content states each screen owes real UI for (§6.4). Reach for it only if a genuinely unbuilt destination needs a placeholder, and delete it once nothing does.
- [core/widgets/not_found_view.dart](lib/src/core/widgets/not_found_view.dart) — the app's **one** generic "not found" state, for a `404` from the API. It is shared because the rule is easy to break one screen at a time: single-item reads answer `404` both for "no such record" and for "exists, but not yours" (§4), so this state must never be phrased as a refusal, and it offers no retry because a `404` is a settled answer. Use it on every new single-item read. Distinct from the router's unknown-route page, which means the app has no screen for a URL and can safely say so.
- [splash](lib/src/features/splash/presentation/splash_screen.dart) — passive, no navigation logic; that lives in the redirect.

**Home and Tasks are each two tab values, not one with a branch behind it.** `/home/student` vs `/home/teacher`, and `/me/tasks` vs `/tasks`, are different endpoints returning different shapes, so something must choose between them; making that choice `ShellTab.studentHome`/`teacherHome` and `ShellTab.studentTasks`/`teacherTasks` keeps it inside `shellTabsFor`, the app's only role check. A single tab whose body asked "am I in the student shell?" would put a role decision back in the widget layer. The tab sets are now **Teacher: Home · My Classes · Library · Tasks · Roster** and **Student: Home · Library · My Tasks · Saved · Profile** — the mobile plan's §1 table with two deliberate differences: Roster is kept for the teacher (it is PRD §5.5.2 and predates the plan), and Saved is not a teacher tab, because a sixth destination will not fit a bottom bar. The teacher reaches Saved through the pushed `/saved` route, from the dashboard.

Tabs are **not routes.** Selection is local `AppShell` state over an `IndexedStack`: a `StatefulShellRoute` needs its branches fixed when the router is built, but the tab set isn't known until `/users/me` answers — and a URL-reachable per-tab route would have to answer "what does a student who deep-links to `/roster` see?" with a role check outside `shellTabsFor`. `/profile` stays a top-level route because the teacher shell pushes to it. Note the `classes` feature folder is unrelated to the demo `classes` feature deleted when this repo was repointed at the PRD (its own repository, model and detail route, nothing to do with `/teacher-assignments`) — do not resurrect that structure or its route shape.

Tests share the fakes in [test/support/](test/support/) — [fake_token_storage.dart](test/support/fake_token_storage.dart) (override `tokenStorageProvider` with it rather than touching the secure-storage platform channel, which has no implementation under `flutter test`), plus [fake_auth_repository.dart](test/support/fake_auth_repository.dart) [fake_profile_repository.dart](test/support/fake_profile_repository.dart) with its `buildMe()` helper, [fake_curriculum_repository.dart](test/support/fake_curriculum_repository.dart) with `buildCurriculum()`, [fake_content_tree_repository.dart](test/support/fake_content_tree_repository.dart) with `buildNode()`/`buildItem()` (whose deep counts default to the node's own items but are settable independently — a greyed branch is a test that passes zeroes), and [fake_teacher_assignment_repository.dart](test/support/fake_teacher_assignment_repository.dart) with `buildAssignment()` (pass `schoolWide: true` for the legacy grant — it nulls all five section/grade fields together, the only shape the API sends) which **records every `teacherId` it was called with**, since the arguments are the only thing that catches a regression to the unscoped call, [fake_section_repository.dart](test/support/fake_section_repository.dart) with `buildSection()` (defaults to a row carrying the server's composed `label`; pass `label: null`, and `gradeLevelName: null` alongside it, for the two fallback forms), and [fake_student_repository.dart](test/support/fake_student_repository.dart) with `buildStudent()`/`buildStudents(n)` — which, unlike the flat-list fakes, *implements* the endpoint (it filters and slices, so a paging test can scroll ninety students through pages of twenty) and **records every query it was called with**, since a filter that quietly wasn't sent returns a plausible-looking screenful either way. [fake_bookmark_repository.dart](test/support/fake_bookmark_repository.dart) with `buildBookmark()` and [fake_task_repository.dart](test/support/fake_task_repository.dart) with `buildTask()`/`buildStudentTask()`/`buildAssignment()` both **record every write's arguments**, for the same reason the progress and student fakes do: a toggle that sent the wrong resource type, a remove that sent no bookmark id, or a create that sent both a `sectionId` and `studentIds` all return a plausible response either way (`FakeTaskRepository` also takes `unreachable:` to exercise the `422` path). [fake_collection_repository.dart](test/support/fake_collection_repository.dart) and [fake_search_repository.dart](test/support/fake_search_repository.dart) *implement* their endpoints — the collection fake mutates on create/rename/delete, and the search fake records every query and slices by cursor, which is what makes a debounce assertion and a paging test real. Every shell test needs the curriculum, teacher-assignment, student *and* section repositories overridden — the shells' tabs are all built up front by the shell's `IndexedStack`, so an unoverridden one goes to the network. Assert an appended page through the controller rather than by finding row text: a `ListView` disposes rows scrolled far off screen, so "is it in the list?" and "is it painted?" are different questions. **Any test that pumps the real app must spread [activityOverrides()](test/support/activity_overrides.dart)** into its overrides. It supplies the in-memory outbox and activity-cache stores plus fake progress/history/home/bookmark/collection/search/task/task-progress/notification repositories — without it the Drift store opens a file through `path_provider`, which has no implementation under `flutter test`. **Every repository behind every tab of either shell must be in there**, because the shell's `IndexedStack` builds all of them up front; the bookmark fake is needed even off the Saved tab, since the save toggle in the player and reader app bars reads the same list, and the **notification** fake is needed on every tab of both shells, since the shell's app bar draws its unread badge off that list. [fake_task_progress_repository.dart](test/support/fake_task_progress_repository.dart) (`buildProgressRow()`/`buildClassProgressRow()`) takes `remindedCount:` — setting it to `0` is how a test exercises the per-day reminder dedupe, which is indistinguishable on the wire from "nobody was pending" — and records every remind and every class-progress query. [fake_notification_repository.dart](test/support/fake_notification_repository.dart) (`buildNotification()`, plus `FakePushTokenSource` for the registration path) *implements* its endpoints, slicing by cursor and flipping `readAt`, and records every read, preference write and device call. Note that the profile body is a `ListView`: a control below the fold has not been **built**, so no finder can match it — tests reaching sign-out must `scrollUntilVisible` rather than `ensureVisible`. Note also that `ActivitySyncController.flush()` really drains in a widget test, so after a `pumpAndSettle` the outbox is *empty* and the fake repository's argument log — not the queue — is what proves a write happened. [fake_progress_repository.dart](test/support/fake_progress_repository.dart) **records every call's arguments**, since a beat that quietly sent the wrong intervals — or a `clientUpdatedAt` stamped at send time — returns a plausible response either way; [fake_history_repository.dart](test/support/fake_history_repository.dart) *implements* the endpoint (filters and slices by cursor) so a paging test is real. Both shells open on Home, so a test wanting the Library, My Classes or Profile tab calls [openShellTab](test/support/shell_navigation.dart) rather than relying on tab order. Note two traps the activity tests hit: `ActivitySyncController` deliberately does not await its own flush, so a test must drain the microtask queue before asserting on what reached the network; and the auto-disposing controllers need a standing `container.listen` or they are torn down the instant an `await` yields. Feature tests pump the real `SmartTeacherApp` against overridden repository providers, so the router redirect is exercised too — see [test/features/auth/](test/features/auth/).

- **The teacher's reports, §5.9** — `TaskProgressRepository` is a second repository over the same records as `TaskRepository`, deliberately: that one owns a task's *lifecycle* (create, edit, cancel), this one owns what has happened against it. [TaskProgressScreen](lib/src/features/tasks/presentation/task_progress_screen.dart) is **one unfiltered read split into three tabs client-side**, even though `/tasks/:id/progress` accepts `?status=`: three separately-fetched subsets would let the tab counts disagree about the size of the class, and *Remind pending* needs the pending count for the whole list rather than for the tab in view. **`{ reminded: 0 }` is ambiguous on the wire** and [TaskProgressController.remindPending](lib/src/features/tasks/presentation/task_progress_controller.dart) is where it stops being — the server dedupes per UTC day through a unique `(taskAssignmentId, sentOn)` index and swallows the `P2002`, so zero means *either* "already sent today" *or* "nobody was pending", and only the caller holding the rows can tell them apart. §5.9 names the first of those explicitly: report "Reminder already sent today", never a send that did not happen. The individual report (`/tasks/:id/students/:studentId`) has **three** answers, not two: a row, a `null` that is the documented "never opened this" and is rendered as such rather than as a zeroed bar, and a `404` that is "no such student **or** not yours" and gets `NotFoundView`. Class progress (`/teacher/class-progress`) builds its section filter from `/home/teacher`'s classes — the `TeacherClassScopeService`-resolved set, like the assign flow — and **not** from the school-wide `/sections`, which would offer sections this endpoint answers `404` for.
- [features/notifications](lib/src/features/notifications/) — the inbox, preferences and push (§5.10). The inbox is cursor-paged like History, but **`notificationPageSize` is 21 because the server hardcodes `take: 21` and accepts no `limit`** — that is its number read off its own query, not a client preference. Marking one row read is **optimistic and goes through the outbox** (`OutboxKind.notificationRead`, whose coalescing rule is plain dedupe): the tap is almost always followed immediately by the navigation to the task it links to, so a write living only in the screen's future would be lost exactly when it is most likely to be made. *Mark all read* is deliberately **not** outboxed — it is a bulk write whose count the user is shown, and one queue entry standing for an unknown number of rows could not be coalesced honestly. Where a notification opens is [notificationTaskPathProvider](lib/src/features/notifications/presentation/notification_deep_link.dart), and it is **not** a second role check: the same `TASK_ASSIGNED` row is `/tasks/:id` for its author and `/my-tasks/:id` for a recipient, so the provider asks which Tasks destination `shellTabsFor` handed out, exactly as the shell asks about the profile action. A role with neither falls back to the inbox rather than pushing a route it would be refused.
- **The unread badge** lives in the shell's app bar for **both** roles — not a tab, since every tab set is already at five — and its count is [unreadNotificationCount](lib/src/features/notifications/presentation/notifications_controller.dart), a plain **function** over the watched `AsyncValue`. It is not a derived `Provider` and must not become one: a `Provider` watching the inbox self-invalidates whenever the inbox rebuilds, and because the badge reads it from inside a widget build, a session change lands mid-frame and asserts `setState() called during build`. For the same reason `notificationsControllerProvider` is cleared by `sessionResetProvider` rather than by `invalidateOnSignOut` — the shell *watches* it, and [session_reset.dart](lib/src/session_reset.dart) already explains at length why a shell-watched provider must be reset on sign-**in** and not invalidated at sign-out.
- **Push is a port, not an integration.** [PushTokenSource](lib/src/features/notifications/domain/push_token_source.dart) is the client mirror of the backend's own `PushService` adapter with its `PUSH_PROVIDER=none`, and [NoopPushTokenSource](lib/src/features/notifications/domain/push_token_source.dart) is the wired default: it answers `null`, so nothing registers and the inbox carries everything — which is precisely the behaviour §5.10 asks for when push permission is denied, meaning the degraded path is the one that is already built and tested. Wiring FCM later is one override of `pushTokenSourceProvider` plus the native config. `currentPushPlatform` answers `null` off iOS/Android rather than guessing, because the DTO is `@IsIn(['ios', 'android'])` and a desktop or test build registering as `'android'` would be a lie that earns a `400`. [PushRegistrationController.register](lib/src/features/notifications/presentation/push_registration_controller.dart) rides `sessionResetProvider`'s transition *into* authenticated, which covers login and a restored session alike; `unregister()` is the **first** step of `LogoutController.logout` and is awaited, because `DELETE /me/devices/:id` is bearer-authenticated and clearing storage first would strand the row that a later push would be delivered to.

What remains after phase 5: nothing from the mobile plan except its open items — the FCM provider above (§8.4), the `Document.pageCount` back-fill (§8.2, which the reader and the student report both already degrade for), and offline search (§8.3, explicitly out of scope). The flat `/videos` and `/documents` lists are PRD §5.4.3 and were never in the plan's phases.

### Theming

[AppTheme](lib/src/core/theme/app_theme.dart) builds light and dark from one `ColorScheme.fromSeed(AppColors.seed)` plus shared component styling — change the seed in [app_colors.dart](lib/src/core/theme/app_colors.dart), not individual widget colors. [ThemeController](lib/src/core/theme/theme_controller.dart) is a Riverpod `Notifier<ThemeMode>` and is **in-memory only**; persistence would go inside its `build`/`set` without touching consumers.

Spacing, radius and animation duration come from `AppConstants` in [app_constants.dart](lib/src/core/constants/app_constants.dart) — use that scale rather than raw numbers. Feature-specific constants stay in the feature folder.
